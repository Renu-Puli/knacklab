1. ROOT CAUSE & BUG CONTEXT
--------------------------------------------------------------------------------
During STEP 5 (BREAK, Medium difficulty), `apps/api/app/worker.py` was modified:
- `click_event_id` was omitted from the `insert(ClickEvent).values(...)` statement.
- The PostgreSQL conflict deduplication clause `.on_conflict_do_nothing(index_elements=["click_event_id"])`
  was removed.

Because Celery / Redis operates under at-least-once delivery semantics, any task
retry (e.g. following a worker crash, network blip, or timeout before ACK) caused the
worker to insert a second, duplicate row into PostgreSQL. This corrupted analytics metrics
by double-counting clicks and violating idempotency requirements.

2. PRE-FIX INSPECTION FINDINGS
--------------------------------------------------------------------------------
Phase 1 requirements were satisfied via comprehensive inspection:

a) Job Payload & Producer:
   - Producer: `apps/api/app/routers/redirect.py` in `_dispatch_click_event()`.
   - Event Identifier: `click_event_id = f"click_{request_id}"`, tying the click event
     directly to the unique HTTP redirect request ID.
   - Privacy: Client IP is hashed via SHA-256 (`hashlib.sha256(ip.encode()).hexdigest()`),
     preventing raw IP storage.
   - Payload: Contains `click_event_id`, `link_id`, `clicked_at`, `user_agent`, `referrer`, and `ip_hash`.

b) Worker & Producer Queue Matching:
   - Both producer and worker connect to Celery default queue `celery` on broker
     `redis://localhost:6379/0`.
   - Task binding: `name="app.worker.record_click_event_task"`.
   - Consumer queue verified: `celery exchange=celery(direct) key=celery`.

c) PostgreSQL Uniqueness Constraints & Indexes:
   - Unique Index: `click_events_click_event_id_key` (UNIQUE btree on `click_event_id`).
   - Normal Index: `ix_click_events_click_event_id` (btree on `click_event_id`).
   - Database enforces row-level uniqueness on `click_event_id` in PostgreSQL.

3. FIX APPLIED
--------------------------------------------------------------------------------
In `apps/api/app/worker.py`, restored atomic idempotent insertion in `record_click_event_task`:

```python
    db: Session = SessionLocal()
    try:
        # Atomic idempotency: insert with ON CONFLICT (click_event_id) DO NOTHING
        stmt = insert(ClickEvent).values(
            click_event_id=click_event_id,
            link_id=link_id,
            clicked_at=clicked_at_dt,
            user_agent=user_agent[:512] if user_agent else None,
            referrer=referrer[:1024] if referrer else None,
            ip_hash=ip_hash,
        )
        if click_event_id:
            stmt = stmt.on_conflict_do_nothing(index_elements=["click_event_id"])
        stmt = stmt.returning(ClickEvent.id)

        result = db.execute(stmt)
        inserted_id = result.scalar_one_or_none()
        db.commit()

        if inserted_id is None and click_event_id:
            logger.info(f"Duplicate click event ignored for click_event_id={click_event_id}")
            return {"status": "deduplicated", "click_event_id": click_event_id}

        return {"status": "recorded", "click_event_id": click_event_id, "link_id": link_id, "id": inserted_id}
```

Key Architectural Properties:
1. Database-Level Enforcement: Leverages PostgreSQL's `ON CONFLICT (click_event_id) DO NOTHING`.
2. Clean Worker Return: If conflict occurs, `inserted_id` is `None`, and worker returns
   `{"status": "deduplicated", "click_event_id": click_event_id}` without raising an error.
3. No Double Counting: Database row count and `/links/{id}/analytics` metrics remain exactly 1.
