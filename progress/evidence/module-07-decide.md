**Selected Choice**: **Option B – Asynchronous Analytics via Queue Worker**

---

## 1. Architectural Trade-off Analysis: Option A vs. Option B

| Dimension | Option A: Synchronous Analytics Write | Option B: Asynchronous Analytics via Queue Worker (Selected) |
| :--- | :--- | :--- |
| **Redirect Request Latency** | **Slow**: Blocked on database network round-trip, disk I/O, row locks, and transaction commit. | **Ultra-Fast**: Light memory enqueue operation; HTTP 307 redirect returned immediately. |
| **System Uptime & Decoupling** | **Coupled**: Any slow query, database lock contention, or connection pool spike on analytics degrades redirect throughput. | **Decoupled**: Public redirect path is completely isolated from database write latency and connection pool pressure. |
| **Surge / Burst Tolerance** | **Fragile**: Traffic spikes directly overwhelm PostgreSQL with write transactions. | **Resilient**: Queue acts as a buffer absorbing traffic surges; worker consumers process and batch insert at a sustainable rate. |
| **Operational Complexity** | Low: In-process database transaction. | Moderate: Requires message broker (e.g. Redis list/stream), worker process, and retry policies. |
| **Failure Modes** | DB latency stalls redirects; DB error risks failing user redirect or losing analytics. | Queue failure handled via best-effort degradation; worker failure handled via bounded retries and dead-lettering. |

---

## 2. Architectural Rationale

Our B2B multi-tenant URL shortener prioritizes the public redirect path. Analytics should not make redirects slower or cause them to fail. Separating click-event processing from the redirect request improves latency and resilience:
1. **Hot-Path Isolation**: Redirects represent >99% of user traffic. Resolving destinations via Redis/PostgreSQL and offloading analytics to a queue guarantees low and predictable redirect latencies.
2. **Buffer Absorption**: The queue absorbs viral click surges, protecting PostgreSQL from connection exhaustion and disk I/O bottlenecks.
3. **Controlled Batching**: Dedicated workers can batch click events into bulk inserts (`executemany`), maximizing database write throughput.

---

## 3. Responses to Official Probing Questions

### 1. What happens when the database is slow?
- Under Option A (synchronous), database slow queries or lock contention immediately stall the ASGI thread/connection, ballooning redirect latency from ~50ms to hundreds of milliseconds or seconds, ultimately exhausting connection pools.
- Under Option B (asynchronous), database slowness has **zero impact on public redirect latency**. The queue naturally buffers incoming events. Workers continue processing in the background, keeping redirect responses immediate.

### 2. What happens when the queue is down?
- If the queue connection fails or is unavailable, the redirect **must still succeed immediately (HTTP 307)**.
- Analytics events can be dropped or buffered locally under a defined best-effort policy.
- Failures must be logged with the request correlation ID (`request_id`) and surfaced in observability metrics. Under no circumstances should an HTTP 500 error be returned to an end user solely because analytics enqueueing failed.

### 3. What is acceptable data loss for analytics?
- Analytical telemetry is non-critical compared with redirect availability. A link that fails to redirect is a severe business outage; a dropped click event during a severe queue infrastructure failure is an acceptable degradation.
- However, data loss must never be silent: queue dropped events must be monitored and measured with explicit metrics and structured error logs.

## 4. Idempotency & Delivery Semantics

- **Realistic Delivery Semantics**: We employ **at-least-once delivery** with **idempotent consumption** (rather than claiming unachievable pure exactly-once transport).
- **Idempotency Key**: Each click event includes a stable, unique identifier: `idempotency_key = f"click:{request_id}"` (using the cryptographically unique `request_id` generated by `RequestIdMiddleware`).
- **Deduplication**: Retried messages retain the exact same `request_id`. Database constraints (or an atomic Redis set check with TTL) prevent duplicate inserts, ensuring analytics metrics and billing aggregations remain completely accurate.

---

## 5. Multi-Tenant Isolation

- **Tenant Identity Preservation**: Enqueued click events store the authoritative `link_id` and organizational scoping (`created_by`).
- **Zero Client Spoofing**: Tenant identity is determined authoritatively by the owning link record, never by client-supplied HTTP headers on public redirects.
- **Isolated Aggregations**: Worker storage and downstream analytics queries strictly filter by `created_by`, maintaining the tenant isolation boundaries established in Module 04.
