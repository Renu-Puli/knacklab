1. ARCHITECTURAL IMPLEMENTATION OVERVIEW
--------------------------------------------------------------------------------
A. Asynchronous Redis Client (apps/api/app/cache.py):
   - Client: redis.asyncio (redis-py v8.1.0) with connection pool.
   - Timeouts: socket_connect_timeout=2.0s, socket_timeout=1.0s, health_check_interval=30s.
   - Lifecycle: Async lifespan manager in app/main.py (init_redis on startup, close_redis on shutdown).
   - Metrics: In-memory observability counters for hits, misses, errors, and invalidations.

B. Cache Service Helpers & Multi-Tenant Scoping:
   - get_redirect_target(code):
     Retrieves cached JSON payload {"long_url", "org_id", "link_id", "expires_at", "cached_at"}.
     Validates explicit link expiration; purges expired entries automatically.
     Returns None on cache miss or Redis failure to trigger PostgreSQL fallback.
   - set_redirect_target(code, long_url, ttl_seconds, org_id, link_id, expires_at):
     Populates cache with short link metadata including tenant org_id.
     Caps TTL based on link.expires_at to ensure cache never outlives link validity.
   - invalidate_redirect_target(code, org_id):
     Evicts cached key "link:{code}".
     Enforces tenant scoping: rejects invalidation if requesting tenant does not own the entry.

C. Redirect Flow Integration (apps/api/app/routers/redirect.py):
   - GET /r/{code}:
     1. Checks Redis cache first via get_redirect_target(code).
     2. Cache Hit -> Returns HTTP 307 immediately with Location header; records click analytics.
     3. Cache Miss / Redis Error -> Queries PostgreSQL source of truth; on success populates Redis with TTL; returns HTTP 307.
     4. Redis Down Graceful Degradation -> Catches RedisError/socket timeouts, logs warning, falls back seamlessly to PostgreSQL.
   - Direct invocation dual-compatibility:
     DualRedirectResponse supports both synchronous direct function invocations (Module 03 unit tests)
     and asynchronous ASGI HTTP pipelines (uvicorn/TestClient) without event loop conflicts.

D. Administrative Invalidation (apps/api/app/routers/links.py):
   - PATCH /links/{id}:
     Updates target long_url, expires_at, or tags within tenant scope (created_by == principal.org_id).
     Commits to PostgreSQL and invalidates Redis cache entry via invalidate_redirect_target.
   - DELETE /links/{id}:
     Deletes record within tenant scope and invalidates Redis cache entry.

5. DOCUMENTED CONSISTENCY LIMITATION & PRODUCTION-HARDENING RISK
--------------------------------------------------------------------------------
- PostgreSQL Update Commit Precedes Redis Invalidation:
  In update_link (PATCH /links/{id}), db.commit() commits changes to PostgreSQL
  before invalidate_redirect_target() attempts cache key eviction.
- Single Invalidation Attempt:
  Redis invalidation makes a single deletion attempt. There is no in-flight retry loop
  or exponential backoff.
- Error Isolation on Invalidation Failure:
  If Redis is unavailable or times out during invalidation, the exception is caught,
  logged as a WARNING with request_id correlation in structured JSON logs, but the
  API continues and returns HTTP 200 OK.
- Bounded Stale-Cache Lifetime:
  Recovery relies on TTL expiration, which is up to 3,600 seconds (1 hour) for standard
  links, or bounded by seconds_until_expiry for expiring links.
- Absence of Async Retry Worker / Transactional Outbox:
  No transactional outbox table or background retry queue (e.g., Celery/ARQ/streams)
  currently exists to asynchronously guarantee eventual cache eviction.
