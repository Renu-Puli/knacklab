Root Cause:
When an authenticated user issues a `PATCH /links/{id}` to update the target `long_url`,
the database transaction succeeds and commits the new destination to PostgreSQL.
However, because the `invalidate_redirect_target` invocation was omitted, the corresponding
Redis cache key (`link:{code}`) is never deleted or updated.
Because public redirects (`GET /r/{code}`) employ a Cache-Aside strategy that checks Redis
first before querying PostgreSQL, subsequent visitors continue to be served the stale,
outdated destination cached in Redis until the key's TTL expires.

--------------------------------------------------------------------------------
2. AFFECTED API BEHAVIOR & SECURITY / CONSISTENCY PROPERTIES
--------------------------------------------------------------------------------
- Data Consistency Violation:
  The database (PostgreSQL source of truth) holds the updated destination URL, but the
  cache (Redis) continues serving the old destination.
- Stale Reads / User Confusion:
  The administrative client receives HTTP 200 OK with the new target URL, but end users
  clicking the short link are redirected to the old URL.
- Security / Phishing Risk:
  If a link is updated to mitigate a compromised or malicious destination, the redirect
  continues delivering traffic to the old destination for up to 1 hour (TTL).
